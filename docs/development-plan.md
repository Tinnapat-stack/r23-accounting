## 3. แนวทางที่ยึดในการพัฒนา

- ระบบอ่านสลิปมีหน้าที่ช่วยกรอกข้อมูล ไม่ใช่ยืนยันว่าเงินเข้าจริง
- สมาชิกส่งสลิปแล้วต้องอยู่ในสถานะ “รอตรวจสอบ” และยังไม่เพิ่มยอดรายรับ
- เหรัญญิกตรวจยอดเงินเข้าจากธนาคารก่อนกดยืนยัน แอดมินตรวจได้เมื่อได้รับสิทธิ์ด้านการเงินเท่านั้น
- ทุกการยืนยัน ปฏิเสธ ยกเลิก หรือเปลี่ยนข้อมูลสำคัญ ต้องมีผู้ทำรายการ เวลา และเหตุผลเมื่อเกี่ยวข้อง
- ตรวจสิทธิ์ที่ระบบหลังบ้านทุกครั้ง ไม่พึ่งการซ่อนปุ่มบนหน้าเว็บ
- ไม่ลบรายการบัญชีที่ยืนยันแล้วเพื่อแก้ความผิดพลาด ให้ใช้การยกเลิกหรือรายการปรับปรุงที่ตรวจสอบย้อนหลังได้
- ยอดเงินต้องคำนวณจากรายการที่ผ่านสถานะที่ถูกต้อง เก็บจำนวนเงินเป็นหน่วยสตางค์หรือชนิดเลขฐานสิบที่แน่นอน
- ยอดเงินสดคงเหลือกับงบที่ใช้ได้เป็นคนละค่า: เงินสดคำนวณจากยอดยกมา + รายรับยืนยัน − รายจ่ายที่จ่ายแล้ว ส่วนงบใช้ได้ต้องหักงบที่กันไว้ด้วย
- **เป้าหมายหลักคือความโปร่งใสต่อทั้งรุ่น:** สมาชิกทุกคนต้องเห็นยอดเงินกองกลางทั้งหมด และเห็นว่าเงินถูกใช้ไปกับอะไรบ้าง พร้อมหลักฐาน (ใบเสร็จเปิดดูได้ทุกคน) ส่วนข้อมูลการจ่ายของคนอื่น สมาชิกเห็นเฉพาะตัวเลขรวม ไม่เห็นรายชื่อ (ตกลง 4 ต.ค. 2569)

## 4. ลำดับการพัฒนาและเกณฑ์ผ่าน

### ระยะ 0 — กำหนดกติกาและขอบเขต

ต้องสรุปก่อนเริ่มออกแบบฐานข้อมูล:

- [ ] ใครเป็นสมาชิก และใช้ข้อมูลใดระบุตัวตน เช่น รหัสนิสิต
- [ ] เก็บเงินรายการอะไร ใครต้องจ่าย จำนวนเท่าไร และครบกำหนดเมื่อใด
- [ ] อนุญาตจ่ายบางส่วน จ่ายเกิน จ่ายแทน หรือคืนเงินหรือไม่
- [ ] ใครตรวจสลิป ใครอนุมัติ และใครจ่ายเงิน
- [ ] บัญชีธนาคารรับเงินและผู้มีสิทธิ์ตรวจรายการเดินบัญชี
- [ ] ยอดยกมา ณ วันเริ่มใช้ พร้อมหลักฐานและผู้รับรอง
- [ ] ขอบเขตข้อมูลที่สมาชิกเห็น และระยะเวลาเก็บสลิป/ข้อมูลส่วนบุคคล
- [ ] เลือกเทคโนโลยี ที่ติดตั้งระบบ และงบดำเนินงาน โดยยังไม่ผูกกับผู้ให้บริการในแผนนี้

**ข้อสรุปที่ตกลงแล้ว (3 ต.ค. 2569):**

- เทคโนโลยี: Supabase (Postgres + Auth + Storage + Realtime) คู่กับหน้าเว็บ
- เข้าสู่ระบบ: อีเมล + รหัสผ่าน ผูกกับรหัสนิสิตที่แอดมินลงทะเบียนไว้ล่วงหน้า
- การชำระ: รองรับจ่ายบางส่วนและจ่ายเกิน (เก็บเป็นเครดิต) เป็นหลัก ส่วนจ่ายแทนคนอื่นและคืนเงินรองรับด้วยแต่เป็นลำดับรอง
- ผู้ตรวจสลิป: เหรัญญิกหลายคนช่วยกันตรวจ ต้องกันการยืนยันรายการเดียวกันซ้ำ
- การเบิกจ่าย: เหรัญญิกอนุมัติคำขอเบิกของตัวเองได้ (ยกเว้นจากข้อในระยะ 4) แต่ทุกการอนุมัติต้องบันทึกผู้ทำรายการไว้ตรวจย้อนหลัง
- รายการเรียกเก็บ: ไม่กำหนดตายตัว ประธานหรือแอดมินสร้างรายการเรียกเก็บใหม่ผ่านหน้าเว็บเอง (ชื่อ ยอดต่อคน ผู้ต้องจ่าย วันครบกำหนด)
- บัญชีรับเงิน: วางโครงไว้ก่อน แอดมินเพิ่ม/แก้บัญชีจริงผ่านหน้าเว็บภายหลัง ระหว่างพัฒนาใช้บัญชีทดสอบ
- ยอดยกมา: บันทึกภายหลังเป็นรายการปรับปรุงหนึ่งรายการพร้อมหลักฐานและผู้รับรอง ต้องมีก่อนเปิดใช้เงินจริง (ระยะ 5) ถ้าไม่มีเงินเดิมให้ใส่ 0
- รายชื่อสมาชิก: แอดมินเพิ่ม/นำเข้า/แก้ไขผ่านหน้าเว็บภายหลัง

**เกณฑ์ผ่าน:** ได้กติกาที่ใช้ตัดสินรายการเงินจริงและขอบเขตเวอร์ชันแรกชัดเจน กรณีที่ยังไม่รองรับต้องแจ้งผู้ใช้และส่งให้ผู้รับผิดชอบจัดการ ห้ามคำนวณเดาเอง

- [x] สร้างเข้าสู่ระบบ ออกจากระบบ และกระบวนการกู้บัญชี
- [x] กำหนดสิทธิ์สมาชิก เหรัญญิก ประธาน ผู้ตรวจสอบ และแอดมิน (ประธาน/แอดมินสร้างรายการเรียกเก็บได้)
- [x] สร้างที่เก็บสลิปแบบไม่เปิดสาธารณะ ตรวจชนิดและขนาดไฟล์

ข้อมูลหลักที่ต้องออกแบบ ได้แก่ ผู้ใช้ สมาชิก บทบาท/สิทธิ์ กิจกรรม รายการเรียกเก็บ ภาระชำระของสมาชิก การแจ้งชำระ หลักฐาน รายการบัญชี การแจ้งเตือน และประวัติการกระทำ ส่วนคำขอเบิก การอนุมัติ และงบประมาณต้องรองรับการต่อยอดในระยะ 4

**เกณฑ์ผ่าน:** สมาชิกเข้าถึงได้เฉพาะข้อมูลที่อนุญาต การเรียก API หรือเปิดไฟล์โดยตรงไม่สามารถข้ามสิทธิ์ได้

**ผลระยะ 1 (3 ต.ค. 2569):** โค้ดอยู่ที่ `supabase/migrations/0001_init.sql` และ `web/index.html` วิธีติดตั้งอยู่ใน `README.md` ชุดทดสอบ `npm test` (`tests/rls.test.mjs`) ตรวจสิทธิ์ทุกบทบาท การเข้าถึงสลิป การกันลบ/แก้สมุดบัญชีและประวัติการกระทำบน Postgres จริงแล้ว ส่วนที่ยังต้องทดสอบเมื่อมีโปรเจ็กต์ Supabase จริง คือ สมัคร ยืนยันอีเมล เข้าสู่ระบบ และลืมรหัสผ่าน ส่วนการแจ้งเตือนมีตารางแล้ว และการสำรองข้อมูลมีขั้นตอนใน README ทั้งสองส่วนจะเริ่มใช้จริงในระยะ 2 และระยะ 5

### ระยะ 2 — รับสลิปและแจ้งเตือนผู้ตรวจเป็นงานหลัก

สร้างส่วนนี้ให้ใช้งานได้โดยไม่ต้องรอ OCR:

- [x] จัดการสมาชิกและรายการเรียกเก็บ พร้อมยอดค้างรายคน
- [x] สมาชิกกรอกยอด วันเวลา รายการที่ชำระ และแนบสลิป
- [x] บันทึกการแจ้งชำระและหลักฐานสำเร็จก่อนแจ้งว่า “ส่งข้อมูลแล้ว”
- [x] แจ้งเหรัญญิกและแอดมินที่มีสิทธิ์ตรวจผ่านกระดิ่งภายในเว็บ
- [x] เปิดเว็บอยู่แล้วเห็นรายการใหม่โดยไม่ต้องรีเฟรชเอง ด้วยการรับอัปเดตหรือดึงข้อมูลเป็นช่วง
- [x] เก็บแจ้งเตือนไว้ในฐานข้อมูล ผู้ตรวจที่ไม่ได้เปิดเว็บจะเห็นเมื่อกลับเข้ามา
- [x] มีหน้ารวมรายการรอตรวจที่เชื่อถือได้ แม้การแจ้งเตือนชั่วคราวล้มเหลว
- [x] กดแจ้งเตือนแล้วเปิดรายละเอียดสลิปและข้อมูลชำระได้ทันที
- [x] ผู้ตรวจกดยืนยันรับเงินหรือไม่ผ่านพร้อมเหตุผล และสมาชิกได้รับแจ้งผล
- [x] ยืนยันแล้วสร้างรายรับและอัปเดตยอดชำระเพียงครั้งเดียว
- [x] ป้องกันการกดซ้ำ การส่งคำขอซ้ำ และผู้ตรวจสองคนยืนยันรายการเดียวกันพร้อมกัน
- [x] แจ้งเตือนเมื่อพบไฟล์หรือเลขอ้างอิงที่เคยส่ง ทั้งนี้เลขอ้างอิงที่กรอกเองยังต้องตรวจสอบ

ตัวอย่างข้อความ: “สมชาย แจ้งชำระค่ากิจกรรม 500 บาท รอตรวจสอบ” โดยแสดงเฉพาะข้อมูลที่ผู้รับมีสิทธิ์เห็น

กระบวนการหลัก:

```text
สมาชิกส่งสลิป → บันทึกรอตรวจสอบ → แจ้งผู้มีสิทธิ์ตรวจ
→ ผู้ตรวจเปิดรายละเอียดและตรวจเงินเข้าธนาคาร
→ ยืนยัน: บันทึกรายรับ + อัปเดตยอดชำระ + แจ้งสมาชิก
→ ไม่ผ่าน: เก็บเหตุผล + แจ้งสมาชิกให้แก้ไข/ส่งใหม่ โดยเก็บประวัติเดิม
```

## 5. ขอบเขตเวอร์ชันแรกและการติดตามงาน

เวอร์ชันทดลองรับชำระควรมี: เข้าสู่ระบบ → สมาชิก → รายการเรียกเก็บ → ส่งสลิป → แจ้งผู้ตรวจ → ตรวจเงินเข้า → ยืนยัน/ไม่ผ่าน → แจ้งสมาชิก → ดูยอดชำระและประวัติ พร้อมสำรองข้อมูล

OCR เป็นขั้นต่อยอดที่วางไว้ในแผน ส่วนเบิกจ่ายและรายงานต้องครบก่อนเรียกระบบว่าเป็นบัญชีกลางที่ครอบคลุมเงินเข้า–ออกทั้งหมด

ทุกช่องงานในเอกสารนี้ยังเป็นงานที่ต้องทำ ให้ทำเครื่องหมายเสร็จเมื่อมีระบบและหลักฐานการตรวจสอบจริง พร้อมอัปเดตวันที่และข้อจำกัดเมื่อขอบเขตเปลี่ยน
